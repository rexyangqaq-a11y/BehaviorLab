# 用户行为序列仿真器：需求澄清与验收基线

版本：讨论稿 v0.4 · 2026-10-19。本文澄清业务需求，不代表待确认问题已经获得答复。详细模块与时序另见 [详细设计](DETAILED_DESIGN.md)。

## 1. 依据、状态与使用方式

依据包括原始《CODEX_PROJECT_HANDOFF.md》以及后续明确要求：建设真实系统页面；支持用户生成、周期选择、行为规划、行为序列与生成记忆查看；搭起用户生成、事件调度、虚拟时间和调用链路；手机指令、模型内容、截图与图转文允许标注为 Mock；界面入口体现递进关系；补充未来模型、手机 Agent 和 VLM 设计。

本文四种标签有不同含义：**已确认**来自上述明确要求；**暂定**允许调整；**工程默认**是当前实现选择，不是业务要求；**待确认**需要研究或集成信息才能定稿。已经实现不等于业务上必须如此，尚未接入也不等于业务上不需要。

## 2. 系统目标与成功含义

**已确认**：为长期记忆研究生成多个虚拟用户的连续行为数据。研究侧观察稳定信息逐步积累以及偶然行为干扰；首期人设固定，行为可以变化。目标规模是每人月级至一年，先通过少量用户、短周期真实闭环验证，再逐步扩大。

系统生成的是带来源的活动、操作、截图和观察文字。页面里的“生成记忆”目前指这些上游观察文字，不是已提取、融合、验证的长期记忆。系统不以“生成了多少条文字”单独代表成功：还需区分流水线完整、任务目标完成、内容真实性和行为自然性。

| 成功维度 | 要回答的问题 | 证据 |
|---|---|---|
| 工程完整性 | 计划、执行、反馈、截图和描述能否闭环？ | 持久化关联、状态、资产校验、恢复记录 |
| 实际执行效果 | 活动完成、部分完成还是受阻？ | 实际对象数、结束原因、操作与截图 |
| 行为效果 | 用户有差异、跨日有稳定性且不机械重复吗？ | 真实样本、跨日统计与人工证据评审 |
| 数据可用性 | 下游能按用户和虚拟顺序重建事件吗？ | 格式版本、排序键、来源与缺失标识 |

Mock 只验证第一类和部分第四类，不能证明真实 APP 可操作、模型自主性或长期自然性。

## 3. 仿真对象与环境边界

| 对象 | 定义与纳入范围 | 状态 |
|---|---|---|
| 虚拟用户 | 简单固定人设及原始生成条件；上下层共享，同用户上下文连续，不同用户隔离 | 已确认 |
| 用户库 | 创建候选、审核修改、确认入库、选取用户创建任务；任务固化人设快照 | 当前产品方案；审核机制为工程设计 |
| 仿真任务 Run | 一组用户、一个虚拟日期区间、时区、APP 能力范围和生成要求 | 已确认的业务组织方式 |
| 每日计划 | 上层生成的当天活动基线；允许无手机活动的空白时段，不必填满全天 | 已确认 |
| 活动 | 一次有目标、工作量和结束条件的操作任务；不同活动可不相关 | 已确认 |
| APP | 新闻、美食、旅游、社区、商城等日常场景；今日头条、大众点评、携程、美团、12306、小红书等为候选 | 用户提供的方向与举例；首个真实 APP 未选定 |
| 手机环境 | 真机或可操作环境提供真实页面，模型逐步理解和决策 | 目标已确认；设备、系统、连接待确认 |
| APP 世界状态 | 不按虚拟日期重建真实 APP 内容、历史价格或库存；保留真实采集时间 | 不建设复杂状态仿真是既有边界 |
| 记忆研究系统 | 接收本系统输出；记忆提取、融合、更新、检索不在本系统内 | 已确认 |

不能声称虚拟用户代表真实人口分布，不能把真实 APP 的同一共享账号环境解释为用户间完全独立。数据上下文隔离和 APP 推荐环境隔离是两件事。

## 4. 时间、周期与顺序

**已确认**：提供周期选择；面向月级至一年，但首期先短周期验证。按用户优先连续生成，再处理下一用户。真实采集可以连续运行，把不同内容对象映射到虚拟日程，不实际等待数月。

**工程默认**：配置采用闭区间起止日期与 IANA 时区；每日按需规划，不预生成全年；事件采用活动虚拟时间锚点和活动内顺序。当前并未为每个步骤赋予有研究含义的精确虚拟秒数。日结束的 23:59 是管理进度标记，不是一条实际行为。

必须分别保存：活动计划时间、事件虚拟锚点、动作真实起止、截图真实采集、描述处理时间。异步描述的完成先后不改变事件排序。日期跨度可配置不等于已验证一年真实采集的吞吐、费用与自然性。

**待确认**：跨时区/夏令时的精确换算是否必要；是否需要活动持续时长和步骤级虚拟时间；是否需要不同用户独立周期。未确认前不把虚拟分钟当作实际投入量，工作量以对象数、目标和结束条件表达。

## 5. 功能需求清单

| ID | 特性与业务行为 | 关键边界 / 验收观察 |
|---|---|---|
| F01 | 根据外部条件补全多个简单人设；也可手动创建基准用户 | 原始条件、生成原稿、人工修改、确认值有来源；手动创建不伪造模型调用 |
| F02 | 建立可复用用户库，选取已确认用户创建任务 | 候选与正式用户分离；历史任务使用快照，不随用户库变化 |
| F03 | 配置用户、日期跨度、时区、APP 能力与行为要求 | 配置校验失败不启动任务；APP 名称不代表已实现兼容 |
| F04 | 上层按用户和虚拟日生成计划 | 管理器只请求/保存；不以手写概率代替模型行为决策 |
| F05 | 计划含时间、APP、目标、量化工作量、结束条件 | 允许空计划；不得先编造具体真实页面对象或已完成事实 |
| F06 | 下层根据当前页面执行活动，逐步决定操作和停止 | hipyum 仅是操作工具；页面理解、决策、进度判断与恢复需要下层 Agent |
| F07 | 每次采集的每张图均记录，与动作和活动关联 | 明确 before/after/observation、多图序号、真实时间与资产哈希 |
| F08 | 保存实际结果，区分完成、部分完成、受阻 | 计划 3 个实际 2 个必须记录 2 个；受阻不是伪成功 |
| F09 | 每项活动终态后请求上层调整判断 | 即使无需调整也保存决定；结果落盘在先，下一活动在反馈提交之后 |
| F10 | 保留计划版本并优先局部调整 | 已完成事实不被改写；当前接口调整能力不等同于未来所有决策策略 |
| F11 | 逐图生成原始描述，执行与描述分别推进 | 同活动有序；允许与后续活动执行重叠；描述失败不自动重采手机活动 |
| F12 | 支持查看规划、实际序列、截图、观察文字和调用 | 展示筛选不改变调度；所有页面显示明确任务归属，Mock 显著标识 |
| F13 | 持久化进度，暂停、继续、故障恢复 | 暂停是安全边界请求；不承诺立即停止外部动作；不盲目重放不确定副作用 |
| F14 | 导出可追溯有序数据与完整性状态 | 缺图/缺描述明确标识；计划不冒充实际，原文不被加工覆盖 |
| F15 | 离线检查完整性和行为效果 | 当前只实现工程完整性；行为评估另定，不自动重规划 |
| F16 | 可替换接入人设模型、规划模型、手机 Agent 和 VLM | 模块接口与来源保留；当前内容适配器仍为 Mock |

F01 的字段、候选审核 UI、F02 用户库组织方式属于满足用户生成需求的现行产品设计，不是固定不可改的研究定义。F15 的自动行为评分不能因列入目标而写成已实现。

## 6. 数据需求与格式澄清

**已确认的语义要求**：按用户隔离；保留原始需求与人设；计划/实际分离，虚拟/真实时间分离，原始/加工分离；所有采集截图可追溯；导出排序稳定；缺失和 Mock 可辨别。

**当前工程格式**：schema_version=2；SQLite 保存状态与关系，文件保存图像；导出 events.jsonl（一张采集图对应一个事件）及 run.json（配置、人设、计划、结果、决定、调用和进度），离线检查另出 check-report.json。最终研究消费格式仍待对齐。

| 数据实体 | 必须表达的业务信息 | 不可混淆项 |
|---|---|---|
| User / Persona | 用户 ID、原始条件、固定人设、生成及审核来源 | 模型原稿与人工确认值 |
| DailyPlan / Activity | 用户日、版本、活动关联、目标和预期工作量 | 计划目标与真实页面对象 |
| ExecutionResult | 实际状态、数量、摘要、结束原因、真实时间 | 完成终态与目标全部满足 |
| Attempt / Step | 尝试、步骤顺序、意图、动作结果、恢复证据 | 动作已发送与动作已成功 |
| Screenshot | 活动/步骤/尝试、阶段、序号、路径、哈希、真实时间 | 动作前图与动作后图 |
| Description | 截图关联、原始文本、模型/提示版本、状态、失败与重试 | VLM 观察和已证实用户偏好 |
| ProcessedText | 原文来源、加工文本、原因和授权决定 | 加工文本不能覆盖原始内容 |
| CallSpan | 父子调用、输入输出、模式、状态、错误、时间 | 调用耗时不是用户行为持续时长 |

事件当前排序键为 `[用户序号, 活动虚拟时间, 活动序号, 步骤序号, 截图序号]`；同一活动多张图可有相同虚拟时间。最终是否保留“一图一事件”、需要按活动聚合、是否嵌入图片字节以及额外训练格式，均待下游确认。当前资产导出为引用，必须一并保留 Run 的 assets 目录。

## 7. 约束、假设与非目标

| 类型 | 内容 | 影响 |
|---|---|---|
| 已确认边界 | 本轮固定人设；只保留有限近期实际上下文，不建设另一套复杂记忆系统 | 长周期连贯性需要实验，不能用全量历史提示词掩盖问题 |
| 暂定 | 一次活动限单 APP | 多 APP 需求应升级活动契约，不偷偷通过执行器越界 |
| 暂定 | 多用户首版共享 APP 账号 | 推荐、浏览记录和登录状态会串扰，报告需披露 |
| 已认可假设 | 结果摘要足够支持多数活动后判断 | 若实验不成立，再讨论按需截图/描述补充，不默认阻塞全部描述 |
| 当前设计基线 | 活动结束后逐图描述，同活动有序 | 描述开始时机可调整；不是研究不可变规则 |
| 工程默认 | Node.js 24、SQLite、文件、单机、每 Run 独立状态 | 不是指定技术栈；没有跨 Run 真机全局排他和分布式调度 |
| 工程默认 | 近期实际窗口 5、描述最多尝试 3、辅助生成每批 1–20 | 可替换；并非研究参数定稿 |
| 非目标 | APP 历史状态重建、自动真实交易、记忆引擎、动态人设、完整年度系统一次建完 | 涉及新范围应单独讨论 |

文字改编只有必要兜底与上层判断的方向被认可；允许改什么、如何标记、下游是否使用、人工复核规则尚未确认。行为库、技能库、端侧还是云端 VLM 都是候选技术方案，不是新增硬性要求。

## 8. 可靠性、可观测性与质量要求

1. 活动实际结果可靠提交后再反馈；重启先补已完成结果的反馈，再推进新活动。
2. 外部动作之前保存步骤意图；中断后由执行器重新观察并决定能否继续。系统不承诺跨外部 API 的 exactly-once。
3. 描述成功原文不可因补跑覆盖；保留失败尝试。某图失败应可明确补跑，不触发活动重采。
4. 用户上下文与持久化关联隔离；真实账号和设备环境隔离必须单独验证。
5. 展示执行、反馈、描述、作业状态，不以一个完成标签掩盖积压；导出完整不代表所有活动目标都完成。
6. 原始图像与描述保留来源。隐私脱敏、保留期、模型数据出域与设备日志策略需在真实采集前定稿，不把当前本地 Demo 当生产权限系统。
7. 不预先承诺吞吐或年级成本；实测设备时长、截图量、模型调用、费用、描述积压、恢复耗时。

## 9. 分阶段验收场景

| 场景 | 操作 / 故障注入 | 通过条件 |
|---|---|---|
| A 用户生成 | 生成多候选、修改并只确认部分，重新打开 | 原稿可追溯；仅所选用户入库；任务使用确认快照 |
| B 单活动闭环 | 请求日计划并推进一项活动 | 计划→步骤/图→结果→调整决定完整；Mock 来源明确 |
| C 顺序与隔离 | 两用户多日，描述速度慢于执行 | 用户优先推进；上下文不串；事件虚拟顺序不随描述完成改变 |
| D 结果后中断 | 结果保存后、反馈提交前终止进程 | 重启补反馈，不重采该活动 |
| E 动作中断 | 步骤意图保存后或动作返回前终止 | 不盲目重放；由执行器恢复或进入 needs_attention |
| F 描述失败 | 中间图描述失败，后续补跑 | 同活动不越过失败前项；其他活动可继续；成功项不重复 |
| G 导出缺失 | 删除/损坏测试图或保留未描述项 | 完整标记为假且报告定位证据；不伪造文本补齐 |
| H 最小真实接入 | 一用户一天一个确定 APP，真实模型/操作/VLM | 真实截图与调用可核验；真实路径与 Mock 区分；逐项报告效果限制 |

A–G 为工程验收，H 才提供真实接入证据。自然性、长期稳定性、偶然行为占比等需要单独实验设计，不能从 A–G 通过推出。

### 影响研究结论、应逐步讨论的问题

以上不要求一次回答全部。先完成四组接入信息，再用短周期证据逐项收敛；不因讨论稿列出了选项就启动全部子系统建设。

## 11. 当前状态与文档维护

现有用户库、任务配置、虚拟日调度、计划版本、持久化、执行/描述独立推进、调用链和导出检查真实运行；人设补全内容、规划决定、手机动作、图像及图转文仍是 Mock。当前源码只接受 mode=mock，真实适配器接入还需调整配置校验和装配入口，不能仅更换服务 URL 宣称完成。

本轮交付为需求与设计文档，不修改运行算法。后续每个需求变更应记录：需求 ID、原结论、新结论、来源、影响接口/数据、验收方式。建议下次先确认 Q01–Q04 及真实闭环验收样本，再修订本稿为正式基线。
