## 测试类别与目的（2026-10-21 用户确认）

用户明确分为下面两类，并随后纠正：第一类是常规软件工程测试，不能概括为 DFX；DFX 只覆盖其中一部分。两类按测试对象和验证目的区分，不按自动化/人工区分。

| 类别 | 验证对象与目的 | 典型内容 | 结果口径 |
|---|---|---|---|
| 常规软件工程测试 | 项目软件实现是否满足需求、正确且稳定 | 单元、接口、集成、系统/端到端、回归；功能正确性、持久化、调度顺序、用户隔离、恢复、配置、导出、部署，以及性能等非功能测试 | 用例通过/失败、缺陷、覆盖范围和版本回归结果 |
| GUI 任务效果与性能评测 | 指定框架＋模型组合能否在实际页面完成给定任务，效率与成本如何 | 具体 APP 任务、条件满足、对象去重与有效完成量、跨页面/跨 APP 操作、长活动；任务成功率、部分完成、耗时、动作/请求次数、token 与有效对象成本 | 按任务、组合、环境和判定依据报告结果，不以工程回归通过数代替 GUI 成功率 |

例如，验证“配置保存后刷新仍可读取”“中断后进度不丢失”属于第一类；验证“某框架＋某模型在指定手机/APP 上找到符合条件的餐厅，并完成任务要求”属于第二类。第一类也可以有网页操作和性能测试；第二类同样可以自动执行、自动判定。

## GUI 评测的判定与审核（2026-10-21 用户确认）

- 第一类可以自动化测试。
- 第二类不预设全部自动判分。按具体用例选择自动化评测，或在生成执行结果后，由助手整理轨迹与证据、提出判定，交用户审核。
- 结果报告交用户审核；不限定每个用例必须采用同一种判定方式。

以下是落实上述要求的工程建议，不是用户已经指定的具体实现：

1. 对可确定检查的条件用规则判定，对开放内容、动态页面或证据冲突给出执行后评审；证据不足明确为无法判断，不让模型的完成宣称代替结果证据。
2. 运行状态、截图是否完整、业务完成判定分开。每个子目标关联实际步骤与原图，记录判定方式、规则版本和原因。
3. 耗时、动作/请求数、服务 usage 等可自动统计；任务完成结论按该用例的评审方式产生。报告列出成功、失败、部分完成、无法判断及受阻情况，并明确统计分母。
4. 固定框架/模型/提示、设备/APP 版本、初态和任务口径；公开任务的鸿蒙迁移保留来源与差异。工程故障夹具、公开历史轨迹与本项目真实执行分别报告。
5. 助手初判和用户审核意见分开保留；待审核的初判明确标注，避免被当作用户已确认的结果。

当前实现仍是工程 Mock 验证台与框架验收定义，尚未接通真实 GUI 任务执行、评测或用户审核工作流。本节约定随 v0.4 相关特性交付落实，不宣称这些界面和持久化字段已经实现，也不提前设计后续版本的全部用例。

## 每版交付

每版交付时包含：

- 覆盖该版特性与相关回归的独立测试用例。
- 可实际测试、调试该版功能的界面，并验证实际入口。
- 测试结果、对应证据，以及未验证或仍为 Mock 的范围。

缺少本版用例或测试调试界面，不记为该版完成。可以复用现有组件，具体入口和交互随版确定，保持主导航简洁。

下一版仍以 v0.4 的开源下层 Agent 选型与最小验证为最高优先级。见[版本计划](VERSION_PLAN.md)。
