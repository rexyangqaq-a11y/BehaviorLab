## 3. 先明确哪些验证不消耗模型 tokens

[31 项框架验收定义](V04_FRAMEWORK_TEST_CASES.md)不是 31 次模型调用，也不应默认乘以三个框架、三个模型形成全组合。

- 源码/许可/版本检查、安装、HDC 基础动作、已有 SDK 离线契约、Mock、存储/顺序/隔离测试：可以做到模型请求为 0。
- 模型协议、固定截图理解、坐标或动作格式：用少量固定输入检查。框架有不同必需模型/定位器时，记录真实组合，不能强行当作同模型。
- 短活动验证完整决策循环、完成核对、追踪、停止恢复等；同一条轨迹可支撑多个验收项，减少重复采集。不能仅凭一次成功宣称全部通过。
- 长活动再验证对象去重、上下文续接、无进展退出和有效对象成本。存档 VLM 另行计量，失败补描述不重跑手机。

A 的每模型 4 请求建议为：1 次中文结构化输出、2 张固定截图各一次理解/定位、1 次框架需要的动作协议检查。用例合并或调整时应重算；若框架协议已有充分证据，可以删减。文本连通已完成，无需再发三个 OK 请求。

B、C 以一个选定且兼容的模型或角色组合做比较，不跑全部模型排列；Midscene 和 MobiAgent 优先，Open-AutoGLM 作基线。框架模型兼容性未证实前不能把表内同一模型成本看作可直接运行的承诺。

**C 包含 B，完整预算不得再次加 B。** D 的“100 对象”指每框架合计 100 个去重、实际达到条件的对象；淘宝和京东若要求各 100 个，则 D 和相应 E 用量约翻倍。当前对象分配、SKU 去重与详情深度尚未最终确认。

请求次数包含规划、定位、核验、摘要等所有模型调用；不是手机动作数。一次动作可能调用多个模型，也可能无需调用。E 的截图量是独立的预计值，不能从模型请求数直接推出截图数：必须保留所有实际返回图片，不得为符合预算丢图。短活动先只选 10–20 张做描述质量试验，该小样本可抵扣 E 的后续处理量，不默认对全部短活动截图再跑一遍 VLM。

所有场景默认关闭思考、无搜索/代码工具、缓存命中按 0 估算；不包含人工、手机、服务器、存储和网络成本。

## 6. 如何逐步收紧预算

1. 先固定少量可授权的图片与起始页，校准每个模型的图片 usage 和动作协议；不把文本 OK 当作图像能力通过。
2. 同一初态、任务与完成标准下，跑两候选各 5 个活动；逐请求记录模型、角色、usage、耗时、结束原因、有效对象数和结果证据。
3. 用 `每有效对象输入/输出 tokens`、请求数、截图数和失败率替换本表假设。比较有效达标对象的成本，不比较“每点击成本”或单纯按宣称完成数计算。
4. 模型返回 usage 时直接累计；缓存和思考明细不可重复计总量；超时未返回 usage 记未知并核对控制台，不当 0，不自动重发。
5. 扩大测试前在运行器落实硬限制：请求/输出/步数/时限、停止与恢复，以及当前预计消耗。30% 是估算余量，不是已实现的超额自动停止系统。现有独立探针仅落实三请求、每次最大 32 输出及零重试。

Token Plan 的实际 Credits 应从相同测试时段的控制台明细核对；不同模型、模式分别记录。得到各模型输入/输出 Credits 系数后，才能将 token 场景换算成套餐额度占用。不能拿别的型号的官方示例系数直接套用，也不能把包月已支付金额都当成这几次请求的成本。
