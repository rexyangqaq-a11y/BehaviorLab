# 业务流程与用户创建 v0.3 · 2026-10-18

本轮落实用户提出的两项修改：入口表达递进关系，用户生成有完整的创建与确认过程。复用 v0.2 的调度器、SQLite、执行/描述队列与适配器，保持上下层职责。

## 使用路径

双击 `start-web.cmd`，或运行 `node src/web-server.mjs --port 4317`，打开 `http://127.0.0.1:4317`。后端更新需重启服务。

左侧只保留 **用户库、仿真任务、系统设置**。移除全局当前任务选择器和跨页面暗中继承的任务状态。

1. 用户库 → 创建用户：选择辅助批量生成或手动创建，填写分组与原始说明，再设置人设条件。
2. 检查候选 → 入库：辅助生成先保存候选原稿；允许修改、勾选部分再入库。用户库的待确认候选可恢复原稿。未提交的页面编辑仅在当前表单内，确认入库时才保存修改，不宣称任意未提交表单可跨刷新恢复。
3. 选择已入库用户 → 创建仿真：自动带入所选用户，另设时间跨度、APP 和行为采集要求。创建时固定人设快照。
4. 进入任务：顶部持续显示任务名、用户数、区间和 APP。内部按运行总览 / 行为规划 → 执行记录 → 生成记忆组织，调用调试作为任务内辅助入口。列表只管理任务，不再混放默认任务的运行面板。
5. 执行页可直接按活动或用户日推进；操作始终指向该任务下一个待执行活动，展示筛选不改变调度顺序。

任务使用可刷新、前进/后退的地址 `#/tasks/:id/:stage`。同一浏览器会话内，按任务 ID + 视图保存各自筛选。用户库有独立搜索、分组和选择状态；人设生成调用归属用户详情，不再混入任务调用列表。

## 人设创建的工程选择

以下是可替换的方案，不升级为业务硬要求：

- 辅助生成用于探索一组用户；手动创建用于基准或明确的对照人设。
- 可选共同条件：城市、年龄区间、职业/生活角色、兴趣、生活背景与使用习惯。自然语言说明单独保存。Mock 应用结构化条件，未指定项由模板补全，不承诺理解任意自然语言或满足研究分布。
- 手动创建只要求名称；来源为手动设定，不虚构模型调用。辅助内容经审核仍标 Mock，不改称真实采集数据。
- 人设简单固定；生活习惯送入上层规划上下文，不转成调度器的概率规则。APP 能力、仿真跨度属于任务。
- 每批 1–20 位与年龄输入范围是当前工程边界。没有实现人口统计抽样/配比保证、动态人设、入库后的版本编辑或共享账号隔离。

## 接口与持久化

沿用 `.data/.users.sqlite` 的 batches、generation_calls、profiles 表，无破坏性迁移。

| 接口 | 作用 |
|---|---|
| `POST /api/users/preview` | count、requirements、cohort_name、constraints；逐个真实调用适配器，保存原始请求/返回，批次标 draft，不写 profiles |
| `GET /api/users/drafts/:id` | 恢复已保存候选原稿 |
| `POST /api/users/drafts/:id/commit` | candidates 中含 call_id 与确认后 persona；只允许本批次候选，不可重复确认 |
| `POST /api/users/manual` | 人工来源入库，不产生模型调用 |

全部选择校验后用一个事务入库；错误、跨批次候选不会导致部分写入。辅助人设保存原始条件、生成原稿、确认后字段、修改字段与 call_id；不覆盖生成调用 output。旧 `/api/users/generate` 保留程序化直接入库兼容行为；新界面使用审核流程。

任务只接受已入库用户。候选不能直接开始仿真，确认过程不回写历史任务快照。

## 验证及限制

新增三项测试，覆盖候选跨重开恢复、候选不提前入库、结构化条件、部分确认、原稿/修改分离、重复确认拒绝、跨批次拒绝且无部分写入、手动来源无伪造调用和 API 到任务快照绑定。最终完整 `node --test` **28/28 通过**。首次运行有原中断恢复用例失败；单项复现与完整复跑通过，未稳定复现，未据此修改恢复算法。

浏览器实测：两位候选退出后恢复审核，改名并只确认一位，直接带入单用户一日任务；实际请求当日规划并推进一项活动，保存六张 Mock 图像和六条观察文字。另验证手动创建、搜索、阶段切换、各视图筛选恢复。样本标记“交互验收”，既有用户与任务保留。

模型内容、手机操作、截图字节和逐图描述仍为 Mock；调度、持久化、虚拟时间、来源与调用真实运行。生成记忆仍是上游观察文字。真实接入继续缺少 hipyum、首个 APP、模型/VLM 服务和下层决策方案四组资料。
