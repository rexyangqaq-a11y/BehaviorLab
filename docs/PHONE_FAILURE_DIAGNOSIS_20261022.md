# 真实任务失败的进一步诊断

2026-10-22。在20页汇报PPT完成后，追加读取保留的原始事件、原生解析源码、审核记录与计算器起点截图。没有新增手机命令或真实模型调用，不改36项成绩，也不覆盖用户后续新增的任务/运行。[只读提取脚本](../scripts/phone-failure-audit.mjs)与[核对证据](evidence/20261022-report-release/failure-audit.json)可复查。

## 判断

用户怀疑有依据：测得的是模型、提示协议、框架解析、设备适配与采集条件共同作用的结果。已有四条接入异常修复后真实通过的证据。与此同时，部分失败清楚涉及错误定位、忽视查询条件、违反禁止操作或没有及时结束，不能全部归为“GUI没执行出来”。当前资料不足以给每个根因分配互斥的失败百分比。

分析必须沿同一条链定位：任务与当前图 → 模型原始回复 → 原生解析/坐标转换 → 设备动作/返回 → 动作后的真实画面 → 独立业务判定。设备命令返回成功只能证明调用返回，不能证明点中了目标。

## 1. 已确认的工程问题

原Python输入桥在输入前复用此前点击位置。已经聚焦搜索框后再次点击，可能误触相机或推荐词。修复改用当前焦点输入，而非由观察方代填内容。另有AutoGLM复杂页半尺寸PNG超过2MiB入口限制，改为相同分辨率JPEG并纠正MIME。原生循环还可能把入口异常包装成正常结束，现已增加调用前阻断事件和失败工程状态。

AutoGLM三模型及MobiAgent×Q3.7的四条小红书异常记录，修复后用25次真实请求完成重测，四项均严格通过。这证明接入问题会压低成绩，但不是严格隔离单变量的A/B试验，不能估算每个修复的独立贡献。旧记录按用户要求覆盖，只保留用量摘要，无法重新逐图回放原始失败。

## 2. 具体坐标链：模型认出图标，落点仍然错误

样本：MobiAgent×DeepSeek计算器，`phone_75847d01-7eb6-4447-ac76-b66bbf8fbc19`。真实屏幕2584×1828，模型输入图1292×914。模型说“点击底部计算器”，给出bbox `[700,855,780,935]`。原生Qwen坐标转换按0–1000计算边框中心，得到约 `(1911,1635)`，设备tap与实际HDC输入也使用这一位置。逐图查看，计算器在底栏中更靠左的位置，手机保持在桌面。共五次实际点击，第六次模型回复仍建议同点，保护阻止继续重复。

这里没有证据支持“执行器把正确坐标又缩放错了一次”：日志的数值变换符合原生函数。可确认的是语义目标与输出位置不一致。系统提示只描述bbox格式，没有明确归一化范围；横坐标700–780又接近半尺寸图中计算器的像素位置，因此存在坐标单位混淆的线索。纵坐标也有偏差，不能断言只要乘二就会成功，禁止靠数值大小自动猜单位。

建议把坐标协议做成显式字段：`space=normalized_1000`、模型图尺寸、原屏尺寸、裁剪原点与方向。统一转换一次，保存原bbox、转换结果、实际落点及目标区域。首先用离线合成图的九宫格、四角、不同宽高/旋转测试转换；再在真机上用少量可见目标校准。该建议尚未改变历史协议或运行成绩。

## 4. 截图会影响被测APP，记录完整不能排除此影响

淘宝九组合只有两项通过，至少四项未完成完整目标的样本受到分享截屏弹层干扰。截图触发业务弹层会改变下一步观察，框架可能进入反复关闭或误点。另一次彩色异常预览即使文件可解码，也不代表画面有效。当前证据能确认干扰存在，不能将所有淘宝失败都归给截屏。

应先做零模型的截图副作用实验：相同页面分别采集一次/连续采集，观察前后页面和弹层，区分系统截屏提示与APP监听。比较现有HDC方式和设备确实支持的其他官方采集方式。不要预设某条命令“静默无副作用”。减少冗余留证需同时保留每次真正模型输入和必要动作前后图，不能为提高成绩删掉不利过程。
