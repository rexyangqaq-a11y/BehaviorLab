## 1. 目标与本次阶段

v0.5目标：主仿真调度中的一个手工／Mock上层活动进入用户选择的下层，保存实际完成量、过程证据、停止原因与恢复状态。先完成无手机、无真实模型的离线装配和故障验证，后续真实验收需用户另行恢复执行。

当前只整理并核对需求文档。业务实现未修改；源码仍`0.4.0-preview.10`、现有部署ZIP仍preview.9。需求已写入不表示实现、界面或验收完成；本稿列出的用例均未执行。

## 2. 范围

本版包含：单活动派发与调试、三框架可选择装配、活动与配置冻结、设备排他、动作与观察证据、商品条件核验、活动内去重、实际量统计、有界执行、自动核对与恢复、人工兜底、阶段状态、导出和旧Mock兼容。

本轮不包含：真实人设和上层规划、存档VLM、长期记忆、百对象、跨活动／跨APP去重、跨日多用户真实稳定性、视频断流修复、第二台物理电脑和正式包更新。HDC路线沿用已有基础，不因hipyum资料暂缺而改为硬性等待。

保存配置、查看页面和已有记录不触发模型或设备动作；真实手机、模型、视频、旧队列与设备探测继续暂停。历史四题矩阵和15请求规则不构成本版调用授权。

## 3. 首个活动与上下层职责

本轮确认B01–B03：首个离线案例是商品浏览，从**手机桌面**开始，依次打开指定APP、搜索任务关键词、浏览列表、打开详情核对条件、去重计数，达标或触及停止条件后结束。该起点不扩展为所有后续活动都必须回桌面。

手工／Mock上层明确关键词、商品条件、目标数量与结束边界；下层自主决定具体操作，找不到时如实保存结果，不自行放宽条件。示例“搜索双肩包，浏览2件价格≤200元的商品”用于说明输入形式；具体APP和正式示例参数仍待细化。

活动进入现有调度，遵循用户／虚拟时间和前序反馈顺序。单活动调试至多推进当前可执行的一项活动；界面筛选不改变调度顺序。结果可靠保存后才反馈，已有结果只补缺失反馈，不重新采集活动。

## 4. 商品完成、条件与去重

本轮确认B04–B06：一个商品满足任务条件、已打开详情页、目标信息有证据可核对，计为浏览完成1件。本活动不额外要求浏览规格或评价才能计数；完成口径不表示已证明真实用户充分阅读。

| 情况 | 计数与处理 |
|---|---|
| 首次核实合格商品，详情与目标信息有证据 | 增加1件，关联商品身份、条件结论与证据 |
| 再次打开同商品链接／商品ID | 不增加数量，保留重复观察记录 |
| 同商品不同颜色、尺寸等规格 | 合计仍为1件 |
| 不同店铺销售同款 | 分别核验，各合格商品可分别计数 |
| 明确不符合任务条件 | 不计数，记录不符合项，继续寻找 |
| 必须条件不可见，例如价格未知 | 标记待核实、不计数，继续寻找 |
| 无法判断商品是否与前项重复 | 标记待核实、不计数，继续寻找 |

去重作用域为同一活动。商品ID／链接的实际提取、变体归并与店铺识别方式后续设计；不能把任意URL变化当成新商品，也不能凭标题或截图哈希独立判定业务身份。离线夹具先明确提供身份及证据，不能把夹具通过当成真实页面识别能力通过。

实际量来自已核实商品，不来自点击次数、截图张数、框架自报数字或finish。计划量与实际量分别保存，身份／条件未知字段不补造；待核实商品后续有足够证据时可计入一次，不能重复累计。

## 5. 自主恢复与人工兜底

本轮确认B07–B08：**自动核对与有界恢复优先，人工最后兜底。** 一次响应丢失或程序中断不自动等于需要人工；正常运行应尽量自主完成。

以点击商品后中断为例，系统先在限额内重新获取当前页面并核对保存的活动、动作与商品进度：能确认已打开目标商品时，继续核验；能确认当前状态允许安全继续时，重新决定下一步。不得因为缺少动作返回就推断未发送，也不得直接重发上一次点击。

只有在限定次数／时间内仍不能确认状态、不能安全继续、关键证据不完整或执行器不支持可靠续接时，才进入needs_attention并请求人工处理。新的观察与恢复请求受本活动预算约束，自动恢复不等于HTTP自动重试、无限尝试或自动切换框架／模型。配置失配、设备争用、存储不可写等阻断按其原因保存和展示，不通过人工标记绕过。

| 人工选择 | 业务含义与后续 |
|---|---|
| 已发生 | 保存确认及依据，保留该动作事实，核对当前状态后才能继续；动作发生不自动证明商品已符合条件 |
| 未发生 | 保存确认及依据，从当前状态重新决定下一步；不把旧动作直接当作待重发命令 |
| 仍未知 | 保留未决状态，不继续执行；可结束本次调试，活动仍待处理 |

人工保存标记本身零动作，由用户再显式选择继续或结束。继续仍受暂停、配置、设备排他、当前状态与恢复能力约束；结束保留已核实数量和全部未决说明，不把未知部分改成已完成事实。人工意见与自动判断分别保存，用户结论优先且历史可追溯。

商品信息不足与执行状态不明必须区分：前者按第4节继续找商品；后者先自动核对，解决不了才人工兜底。不得让日常缺价、重复身份不明等情况都阻塞运行并等待人工。

## 6. 停止与结果

本轮确认B09：达到目标即结束；找不到足够商品时，达到预设时间、调用次数或无进展上限后自动停止，不反复请求用户加量。步数和物理输入等工程限额继续沿用有界要求；具体数值待细化。

| 状态 | 判定与必须保留的事实 |
|---|---|
| completed | 目标数量及所需条件已核实，保留商品与完成证据，无未决执行状态 |
| partial | 停止时已有成果但不足目标，实际量与停止原因明确；目标2、实际1须记录1 |
| blocked | 无已核实合格商品且受阻，保留实际0及原因 |
| needs_attention | 自动核对／恢复后执行状态仍不确定或不能安全继续，保留已核实数量、未决项和原因，等待处理 |

未知执行状态优先：即使已核实1件，仍有未决动作时也应展示“已核实1件／待处理”，不能仅用partial遮盖未决项。结束本次调试不自动解决未知状态。禁止操作和约束违反单独记录，不凭框架finish、HTTP成功或终图存在授予completed。

工程退出、业务结果、反馈、描述和导出状态分别呈现。needs_attention处理前不派发后续手机活动、不产生普通终态反馈；已有截图的独立描述处理可按原规则推进。描述失败只补已有图，不重采活动。
